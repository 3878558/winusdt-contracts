# Slots PvC — дизайн-документ (фаза 1)

> **Статус:** черновик на утверждение владельцу. После аппрува → фаза 2:
> Monte-Carlo скрипт математики → `Slots.sol` + тесты → деплой → фронтенд.
>
> PvC = Player vs Casino: игрок крутит против банкролла контракта, а не ждёт
> 9 других игроков. Роль проекта в экономике: лотерея — мультиплеер с медленным
> циклом (собраться 10 игрокам); слоты — мгновенная соло-игра, которая
> создаёт **банкролл-пул** — магнит ликвидности (LP зарабатывают преимущество
> дома) и источник постоянного он-чейн traffic.

## 1. Ключевые решения (TL;DR)

| Параметр | Решение | Почему |
|---|---|---|
| RNG | Две транзакции: `spin()` → `resolve()`; сид = `keccak(blockhash(betBlock+1), player, bet)` | Урок V1: значение **не существует** в момент ставки → снайп-симуляция невозможна |
| Механика | 3 барабана × 8 символов, взвешенные таблицы | Достаточно для интересной математики, просто верифицировать on-chain |
| RTP | 95.0% (включая комиссию) | Единообразие с лотереей (5% edge) |
| Max множитель | ×100 (джекпот 7️⃣7️⃣7️⃣) | Cap против валидатор-атак и для exposure-лимитов |
| Комиссия 5% | **Bootstrap: 100% LP-ам** (параметр `creatorFeeShare=0`, поднимается владельцем позже) | Сначала купить ликвидностьyield-ом, монетизация — после роста TVL |
| Банкролл | LP-пул с долями (shares): депозит → доля → edge капает в пул | Решает проблему ликвидности: повод внести USDT и держать |
| Одновременных спинов | 1 на игрока | Cap exposure, простая бухгалтерия |
| Дедлайн resolve | 256 блоков (~3 мин), потом авто-refund ставки | blockhash(N) доступен 256 блоков; застревание исключено |
| Токен | USDT (BSC, 18 dec), BNB отклоняется | Единообразие с лотереей |

## 2. Игровая математика (кандидат, финал — Monte Carlo в фазе 2)

### 2.1 Механика

Каждый барабан независимо выбирает символ по весам. Сид определяет 3 числа:

```
r1 = seed % W;  r2 = (seed / W) % W;  r3 = (seed / W²) % W
```

символ барабана = первый, чей накопительный вес накрывает r. Выплата —
по правилам ниже, множитель × ставка.

### 2.2 Символы и веса (одинаковы на всех барабанах, W = 72)

Иерархия и иконография — канон слот-традиции: 🍒 самый частый и дешёвый
(платит даже частично — фирменная черта fruit machines), 7️⃣ джекпот
(lucky sevens), фрукты как символы — из эры «резиновых» выплат жевательной
резинкой начала XX века. Конкретные веса и множители — не из практики,
а выведены из уравнения RTP=95% (у реальных машин — PAR-sheets с разными
лентами на каждый барабан). Модель симметричная (одинаковые веса на всех
барабанах) — сознательное упрощение ради тривиальной сторонней верификации;
асимметричные ленты — идея для v2. Wild/scatter/бонус-раунды исключены:
ломают чистую функцию «сид → результат».

### 2.4 Независимость спинов: ставки, кошельки, истории

Сид спина — чистая функция `(blockhash(betBlock+1), player, bet)` без
какого-либо состояния: прошлые спины, серии, смена размера ставки и личность
кошелька не входят в вычисление исхода. Следствия:

- **Смена размера ставки ничего не меняет в вероятностях** — только
  абсолютный масштаб: ожидаемый проигрыш всегда 5% оборота, дисперсия
  пропорциональна ставке. Схемы «поймал серию на max → молоть min» и
  «проиграл на min → агрессивный max» одинаково бессмысленны: у контракта
  нет ни компенсаций, ни «охлаждения», ни памяти.
- **Кошелёк различается только бухгалтерски** (escrow, выплата, лимит
  «1 активный спин»), но не распределением исходов: RTP не
  ребалансируется между кошельками — у каждого спина свои честные 95%.
- Любая зависимость от истории была бы одновременно эксплойтом
  (bet-switching/martingale-схемы стали бы прибыльными) и нарушением
  provably fair (исход перестал бы быть чистой функцией проверяемых входов).
- Глобальная сходимость: aggregate RTP → 95% по всему обороту (закон
  больших чисел по всем кошелькам сразу); локальный плюс отдельного игрока
  — дисперсия, покрываемая слоями 2–4 из §3.4 (exposure guard, maxBet,
  риск разорения), а не «подгонкой» исходов.

Фаза 2 добавляет в симуляцию явный тест: игрок со сменой размеров ставок
(включая «серии на max → переход на min») должен показывать per-unit RTP,
статистически неотличимый от игрока с постоянной ставкой.
## 3. Он-чейн архитектура

### 3.1 Двух-транзакционный спин (главный урок пост-мортема)

```
spin(bet):                          // tx 1 — игрок
  require(bet в [minBet, maxBet])
  require(нет активного спина у игрока)
  require(bankroll ≥ exposure + 100×bet)   // можем ли выплатить джекпот
  escrow(bet)                               // средства заблокированы ДО результата
  spin[player] = Spin(bet, block.number)

resolve():                          // tx 2 — игрок, фронтенд или кто угодно
  s = spin[player]; require(block.number > s.betBlock)
  h = blockhash(s.betBlock + 1)
  if (h == 0) → expireRefund: вернуть bet, спин закрыт   // прошло >256 блоков
  seed = keccak(h, player, s.bet)
  payout = evaluate(seed, s.bet)            // чистая функция, видна в коде
  payout ? pay(player, payout) : (деньги остаются в банкролл)
  delete spin[player]
```

Почему это неуязвимее лотереи V1:

1. В момент tx 1 `blockhash(betBlock+1)` **не существует** — предсказать
   исход нельзя ни боту, ни валидатору-участнику.
2. Средства в escrow до resolve: «проиграл — и не подтвердил» невозможно,
   отменить ставку после mined-блока нельзя. Choice-to-abandon отсутствует.
3. `resolve()` permissionless — РЕШЕНО (2026-11-14): газ resolve по умолчанию
   НА ИГРОКЕ — фронтенд через ~2 c шлёт resolve из кошелька игрока (вторая
   подпись; BSC ≈ $0.003–0.10 за tx). Дом не несёт per-spin расходов в любом
   газовом режиме; keeper — только для брошенных спинов (игрок закрыл
   вкладку) и батчей при газовых пиках. Если игрок офлайн, любой может
   вызвать `resolveFor(player)` (выплата всё равно игроку); застрять
   средства могут максимум на 256 блоков, затем авто-refund ставки.
4. Нонc не нужен: пары `(betBlock+1, player)` уникальны, один активный
   спин на игрока исключает replay.
5. UX/газ-оптимизация (фаза 3): `spin(bet, resolvePrev)` — тот же tx
   закрывает предыдущий спин этого игрока (blockhash его betBlock+1 к
   моменту tx существует). Непрерывная игра = 1 подпись на спин вместо
   двух; отдельные resolve — только на первый и последний спин сессии.
   Серия (spinSeries → resolveSeries) и так амортизирует: 2 подписи на 10
   спинов.

### 3.2 Остаточный риск валидатора (честно)

Валидатор, создающий блок N+1, теоретически может влиять на его хеш
(порядок tx, timestamp). На BSC 21 валидатор, SLA/репутация, доход
валидатора >> потенциальный выигрыш; риск Accepted по рынку (так работают
dice/slot-dApps на BSC годами). Смягчения: cap ×100 на макс. выплату,
лимит `maxBet` от размера банкролла (см. 3.4), один спин на кошелёк.
Опция на будущее (если TVL вырастет): сид из двух блоков
`keccak(blockhash(N+1), blockhash(N+2))` — цена: +1 tx задержки.

### 3.3 Банкролл и LP-доли

```
deposit(usdt)  → shares = amount × totalShares / principal    // первый LP: 1:1
withdraw(shares) → require(остаток ≥ escrow + Σ exposure активных спинов + резерв)
```

- `principal` = депозиты − выводы; `profit` = баланс − principal − escrow.
- **Комиссия виртуальна:** 5% edge не переносится транзакцией — он встроен в
  paytable (EV выплаты = 0.95×bet). LP-доход = статистическая маржа: в
  ожидании баланс растёт на 5% оборота. `creatorFeeShare > 0` материализуется
  как перевод `creatorFeeShare × 5% × bet` создателю на каждом resolve —
  ровно на эту величину маржа LP меньше.
- **Цена доли: (balance − escrow) / totalShares.** Escrow по номиналу
  (истёкший окном — возвращается). Известная ограниченная гонка: вывод LP в
  окне «spin → resolve» (~2 c) может захватить долю escrow до maxBet на
  активный спин — неплатёжеспособности не создаёт (guard слоя 2 держит),
  эффект ограничен и на bootstrap пренебрежим; эпоховый сеттлмент — опция
  фазы 5 при крупном TVL.
- Параметр `creatorFeeShare` (bps): bootstrap = 0 (все 5% LP-ам); владелец
  может поднять до 5000 bps (50/50) когда TVL наберётся. Монетизация
  создателя на старте — не из слотов.
- Вывод LP блокируется только если ломает покрытие активных спинов
  (мгновенный при запасе; иначе «сначала разрекешится, потом уйдёшь»).
- **Expire серии:** v1 — single-shot `resolveSeries` (без чанков); при
  пропуске окна (256 блоков от betBlock+1) — возврат всего escrow серии N×bet.
  Чанковый resolve — оптимизация фазы 5.

### 3.4 Связка RTP ↔ сетка выплат ↔ банкролл (четыре слоя)

**Слой 1 — RTP статичен.** RTP = Σ p×m по сетке выплат; он не зависит от
банкролла, числа игроков и чего-либо ещё. Контракт никогда не подгоняет
выплаты под баланс — это проверялось бы на верифицированном коде за минуту
и разрушило бы provably fair.

**Слой 2 — admission guard: платёжеспособность вместо подгонки.** Ставка
принимается только если банкролл покрывает худший исход ВСЕХ активных спинов:

```
freeBankroll := balance − escrow − Σ 99×bet_активных   // явное определение
require(freeBankroll ≥ 99 × bet)                        // для нового спина
```

Банкролл мал → сжимается допустимая ставка, а не RTP. Инвариант
«3 одновременных худших джекпота» выполняется тождественно:
3 × 99 × maxBet = 3 × 99 × freeBankroll/300 = 0.99 × freeBankroll ≤ freeBankroll.

**Слой 3 — динамический maxBet.**

```
maxBet = freeBankroll / 300, cap 10 USDT (bootstrap)
```

При банкролле 300 → maxBet ≈ 1 USDT; при 3000 → упирается в cap 10.
Коэффициент 300 = маржа на ~3 одновременных худших джекпота (3 × 99×bet)
+ статистическая подушка из слоя 4.

**Слой 4 — риск разорения определяет минимум банкролла.** RTP 95% —
долгосрочное ожидание; в короткой серии σ ≈ 1.9 ставки (джекпот ×100).
Диффузионная оценка риска разорения дома (верифицировано: Var = 3.696,
σ = 1.9225 при финальной таблице):

```
P(ruin) ≈ exp(−2 × edge × B / σ²),  B = банкролл в средних ставках,
edge = 0.05, σ² ≈ 3.70  →  exp(−0.0270 × B)
```

| B (банкролл / средний спин) | P(ruin) |
|---|---|
| 100 (напр. 100 USDT при спине 1) | ~6.8% — слишком рискованно |
| **300 (300 USDT при спине 1)** | **~0.03%** — принимаемо |
| 1000 | ~10⁻¹² |

Отсюда bootstrap-рекомендация ≥300 USDT; при меньшем TVL maxBet формула
слоя 3 автоматически держит спины мелкими, сохраняя ничтожный риск.

**Таблица размеров банкролла одной машины** (maxBet = банкролл/300;
конкурентность = floor(банкролл/99/maxBet) одновременных худших джекпотов):

| Банкролл | maxBet | P(остановка)/год — MC фазы 2 | Конкурентных худших джекпотов |
|---|---|---|---|
| 50 | 0.5 (только minBet) | **92.3%** [91.0…93.4] ⛔ | 1 |
| 100 | 0.5 (только minBet) | **9.1%** [7.9…10.4] ⚠️ | 1 |
| **300 (bootstrap)** | **1** | **0 из 2000 прогонов** [0…0.19] ✅ | **3** |
| 1500 | 5 | 0 из 2000 [0…0.19] ✅ | 5 |
| 3000 | 10 (cap) | 0 из 2000 [0…0.19] ✅ | 10 |

Старые оценки этого параграфа (~7% / ~0.03% / 10⁻⁹ / 10⁻¹²) — наивная
диффузионная аппроксимация без admission-пола; Monte-Carlo фазы 2 (2000
прогонов × 365 дней × 1000 спинов/день, динамический maxBet + admission
+ feeShare 0) — авторитетный источник, см. docs/slots-math.md. Определение:
ruin = операционная остановка (fb < 50, absorbing — нет спинов, нет edge);
insolvency (fb < 0) при admission невозможна механически. Бонус-финдинг:
банкролл 300 самозаживляющийся — 95% дней года с доступным турбо, min fb
p05 ≈ 69% старта.

Банкролл — рабочий капитал, не заморозка: ставки входят, выплаты выходят;
требование — не опускаться ниже floor. Растёт от LP-депозитов → maxBet
поднимается автоматически. В v1 машина = контракт = свой банкролл; общий
банкролл на несколько машин — отдельное решение будущего. LP при 300:
дневная σ ≈ ±61 при edge +50 (1000 спинов/день по 1) — просадки дней
−30…−40% возможны, писать честно на карточке депозита.

**Слой LP:** вывод доли разрешён, только если после него остаётся
`freeBankroll ≥ escrow + Σ 99×bet` активных спинов — LP не может вывести
так, чтобы оставить контракт неспособным выплатить уже принятые ставки.

### 3.6 UX подписей: сколько подписывает игрок

| Событие | Подпись игрока | Газ |
|---|---|---|
| Первый спин сессии | 2: `approve` USDT + `spin()` | Игрок |
| Каждый следующий спин | **1: `spin(bet)`** | Игрок (~0.0001–0.0004 BNB) |
| `resolve()` (~2 c после ставки) | **нет** — permissionless, вызывает кипер | Кипер (~$0.02–0.05) |

Resolve безопасно автоматизировать: исход детерминирован контрактом,
выплата идёт игроку по адресу из маппинга — кипер не может ни выбрать
исход, ни перенаправить средства. Игрок вправе вызвать resolve сам.

**Enhancement (фаза 5): Turbo-серия — N спинов за одну подпись.**
`spinSeries(N)`: escrow N×bet → `resolveSeries()` после N блоков вычисляет
N сидов из N последовательных блоков `blockhash(betBlock+1 … +N)` — ни один
не существовал в момент подписи, provably fair сохраняется. 10 спинов =
1 попап, результат через ~8–10 c. Идеально для турбо-режима UI.

**Ограничители N (три стены):**
1. Банкролл-адмиссия (главная на старте): `N ≤ freeBankroll / (99×bet)` —
   строго worst-case: серия из N джекпотов обязана быть оплачена целиком.
   На bootstrap 300: bet 0.5 → N≤6, bet 1 → N≤3. При TVL 3000: bet 1 → N≤30.
2. Blockhash-окно: N ≤ 255 (EVM хранит хеши ~256 блоков; при 0.75 c/блок
   ~3 мин) — не бьётся раньше стены 1.
3. Газ: N ≤ 64 (все-выиграли ≈ 3.5M gas ≈ $2 киперу на батч — амортизируется).

UX серии: все N×bet списываются в escrow сразу; результаты показываются
прогрессивно (фронтенд читает blockhash по мере майнинга блоков); расчёт и
выплата — одна tx в конце (кипер может дробить на чанки). Отмена серии
невозможна — это цена одной подписи (escrow до конца).

**Переход к турбо (три уровня):**
1. Контракт: `spin` и `spinSeries` — два входа, общая модель «одна активная
   сессия на игрока» (нельзя смешивать; переход всегда через resolve).
   Admission серии happens-at-creation: `freeBankroll ≥ 99×N×bet` (escrow
   в зачёте покрытия) — пущенная серия гарантированно оплачена до конца
   при любом последующем движении TVL.
2. UI: доступность — чистая функция банкролла (`N_max = floor(freeBankroll/
   (99×bet))`): N_max < 3 → турбо скрыт; 3–4 → показан с подсказкой;
   N_max ≥ 10 при bet 1 → маркетинговый «Turbo ×10» (≈ TVL 1000).
   ВНИМАНИЕ: «1000» — это UI-порог показа маркетинговой кнопки при bet=1,
   НЕ правило контракта: контракт принимает любую серию, покрытую
   `freeBankroll ≥ 99×N×bet` (например, банк 500: bet 0.5 → ×10 доступен,
   bet 5 → нет). Никакого админ-включения: LP-депозиты сами открывают
   режим (и сами мотивируются им — «TVL 1000 открывает турбо» пишем на
   карточке банкролла).
3. Роадмап: фаза 4 деплоит ТОЛЬКО solo (меньше поверхность атак в первые
   недели); турбо — фаза 5, когда базовый цикл доказан на мейннете и TVL
   ≥ 1000. Существующие solo при добавлении не мигрируют — входы сосуществуют.
   Просадка TVL саморегулируется: N_max и maxBet сжимаются автоматически,
   уже идущие серии гарантированно оплачены.

Approve-стратегия (решение перед деплоем): точный allowance с повторными
approve vs большой allowance раз в сессию — безопасность/UX trade-off,
прописать в FAQ («почему MetaMask просит разрешение на USDT»).

### 3.7 Газ-экономика и минимальная ставка

Живые данные (2026-11-11): BSC gasPrice ≈ 0.05 gwei (после Maxwell),
BNB ≈ $666. Спин ≈ 150k gas, resolve ≈ 80k gas.

| Газ | Игрок/спин | Кипер/resolve | LP-floor (bet>20×Ck) | Игрок-floor (gas≤2% bet) |
|---|---|---|---|---|
| 0.05 gwei (сейчас) | $0.005 | $0.003 | $0.05 | $0.25 |
| 1 gwei (запас) | $0.10 | $0.10 | $2.00 | $5.00 |
| 3 gwei (пик) | $0.30 | $0.16 | $3.20 | $15.00 |

Два независимых пола: (а) LP — 5% edge со спина должен покрывать киперский
resolve; (б) игрок — газ не должен заметно топить RTP. **Решение:
minBet = 0.5 USDT** — при текущем газе это 1% накладных, при 1 gwei solo-спины
смысль имеют от 1 USDT, а 0.5 живёт в turbo-серии (батчинг 10 спинов на
1 подпись → газ/спин ×0.1). Чип 0.1 исключён: при любом росте газа абсурден.

**Решение (2026-11-14): resolve-газ — на игроке** (§3.1 п.3 и п.5). Дом не
платит за резолвы ни в одном газовом режиме — годовая экономика = валовой
edge минус крохотный keeper-cleanup брошенных спинов. Кипер при дорогом
газе: батчит `resolveSeries`/`resolveFor` (газ/спин /N), ждёт газовые
окна, в пределе приостанавливает авторезолв мелких ставок — игрок резолвит
сам или сработает expire-refund. Тупиков не существует.

**minBet 0.5 vs 1 — Monte-Carlo сравнение (2026-11-14, 50% загрузки = 500
спинов/день, 1000 годовых прогонов на капитал, feeShare 0):**

| Капитал | minBet 0.5 → P(остановка) | minBet 1 → P(остановка) |
|---|---|---|
| 50 | 91.3% [89.4…92.9] ⛔ | stillborn: admission (fb≥100) отвергает все ставки ⛔ |
| 100 | 10.1% [8.4…12.1] ⚠️ | 93.4% [91.7…94.8] ⛔ |
| **300 (bootstrap)** | **0.000% [0…0.38] ✅** | **0.400% [0.16…1.02]** (×13 к наивной оценке) |
| 1500 / 3000 | 0% ✅ | 0% ✅ |

Оборот при 300: 0.5 → 350/день (avg bet 0.7), 1 → 500/день (avg bet 1.0,
+43% edge) — но stop-риск выше, вход для игрока вдвое дороже (спрос = main
bottleneck нового продукта), лестница рвётся (1→5, разрыв ×5). **Решение:
minBet 0.5 остаётся**; подъём до 1 — owner-параметр `setLimits` (тимлок
24ч) при росте спроса/газа, одна tx.

В FAQ: «газ BSC оплачивается отдельно от ставки; обычно <$0.01–0.05 за спин;
RTP 95% считается по ставке, газ не входит».

### 3.8 Подписи и прувы: кто что подписывает

**Подписываются только транзакции** (ECDSA secp256k1, стандартный флоу
MetaMask): `approve` (раз в сессию), `spin(bet)` (каждый спин), `resolve`
(только кипер). Офчейн-подписей (EIP-712, permit) в v1 нет: USDT на BSC
не поддерживает EIP-2612, офчейн-ваучеров в дизайне нет.

**Прувы не подписываются никем** — пруфом является сама цепочка. Схема
верификации: `blockHash` + `player` + `bet` → keccak → веса → символы →
выплата; всё пересчитывается любым желающим за минуту на BscScan.

**Обязательное требование к Slots.sol — события полного разложения:**

```solidity
event SpinStarted(address indexed player, uint256 indexed betBlock, uint256 bet);
event SpinResolved(
    address indexed player,
    uint256 indexed betBlock,
    uint256 bet,
    bytes32 blockHash,   // источник сида — публичный пруф
    uint256 seed,        // полный сид
    uint8[3] symbols,    // индексы символов по барабанам
    uint256 payout
);
```

Причина: `blockhash(N)` в EVM доступен лишь ~256 блоков (~3 мин). Без
события пруф «сгниёт» — с событием каждый спин аудируем навсегда, включая
проверку сторонними инструментами спустя годы. Кнопка «Verify» во фронтенде
берёт поля из события и показывает пересчёт построчно.

### 3.5 Чеклист безопасности (по пост-мортему §7 + trust-protocol)

| Урок V1 | Как выполнен в Slots |
|---|---|
| RNG из текущего tx читается | Сид из **будущего** блока — не существует при ставке |
| Атомарность — оружие атакующего | Ставка escrow-ится; «проверил и отменил» нет |
| Недобор = розыгрыш (подарок) | N/A: PvC, розыгрыш всегда ровно один на ставку |
| Нужен тупик-выход | expireRefund через 256 блоков; owner может pause НОВЫЕ ставки, активные всегда разрешаются/возвращаются |
| Право на ошибку | `paused` + `maxBet`/`creatorFeeShare` как owner-параметры; исходы спинов не зависят от owner |
| Reentrancy | transfers последними, checks-effects-interactions; USDT без fee-on-transfer поддержка явная |
| BNB | `receive` revert |

**Anti-scam требования (docs/trust-protocol.md, §2 — обязательны к
реализации в фазе 3):**
- **Timelock 24ч** на все owner-параметры (`ParamChangeScheduled` → 24ч →
  `ParamChangeApplied` с old/new; сутки на реакцию LP/игроков).
- **Paytable, веса, формула сида — immutable** константы (владелец не может
  изменить — provably fair).
- **Исчерпывающие списки CAN/CANNOT** владельца — в комментарии контракта и
  на странице Security (владелец НЕ может: трогать escrow/призовые,
  выводить principal LP, менять paytable, отменять спины, банить адресов).
- Создатель-LP = обычные доли на общих правилах.

## 4. Экономика: как это решает проблему ликвидности

- **Лотерея** (PvP) ликвидности не требует, но и не создаёт: пул живёт
  минуты и распадается. Ретеншн зависит от «собрать 10 игроков» — узкое
  горлышко (видно на live-статистике: раунды чаще refund-ятся).
- **Слоты** (PvC) создают постоянный актив — банкролл — на который есть
  причина вносить и держать USDT: LP-доходность ≈ 5% × оборот/банкролл.
  При обороте 20× банкролла в месяц это ~100% APR — магнит для депозитов
  из той же аудитории (игроки-держатели USDT).
- Больше банкролл → выше maxBet → интереснее игра → больше оборот →
  больше yield. Петля ликвидности, которой у лотереи нет.
- Соло-игра убивает узкое горлышко ожидания: игрок крутит сразу,
  2 tx ~5 секунд на спин.

### Юнит-экономика bootstrap (черновая)

Банкролл 300 USDT (казна) + LP-депозиты. Средний спин 1 USDT, оборот
100 спинов/день → 3000 USDT/мес оборота → edge 150 USDT/мес → LP APR ≈
50% при TVL 300 → мотивация депозитов растёт → TVL 1000 → APR 15% —
новое равновесие с большей пропускной способностью.

### Монетизация создателя (планки creatorFeeShare)

Два независимых потока дохода создателя от слотов:
1. **LP-доля — с дня 0.** Стартовые 300 USDT из казны заводятся депозитом на
   общих правилах: при TVL 300 создатель = 100% LP и получает весь edge
   (≈150/мес); при росте TVL доля разбавляется, доход сохраняется
   пропорционально капиталу. База, не выключается никогда.
2. **creatorFeeShare — прямой срез edge поверх LP-доли, включается по
   планкам** (ручная tx: тимлок 24ч + анонс; политику публикуем на Security
   и в README зеркала — «0% пока TVL < 1000»):

| Планка | Условие | feeShare | Логика |
|---|---|---|---|
| 0 (bootstrap) | TVL < 1000 | 0 bps | весь edge в банкролл → макс. APR-магнит; создатель живёт на LP-доле |
| A | TVL ≥ 1000 стабильно ≥ 7 дней (турбо открыт) | 2000 bps (20%) | магнит отработал; у LP ещё десятки % APR + уникальный режим |
| B | TVL ≥ 3000 | 3500 bps (35%) | maxBet 5–10 в игре, оборот кратно выше |
| потолок | TVL ≥ 5000, вручную | 5000 bps (50/50) | ручное решение; выше — никогда (contract hard-limit ≤ 5000) |

Механика: feeShare делит ТОЛЬКО реализованный edge на resolve (нетто
раунда), principal LP не трогает; банкролл пополняется на
(1−feeShare)×edge. Выплата создателю — накопление + `claimCreatorFees()`
батчем (не transfer на каждый спин — газ). Планка A привязана к «турбо
открыт», не к календарю: ранний подъём бьёт по ранним депозиторам (= той
же аудитории, что игроки). Автомата по TVL в контракте нет сознательно —
owner-параметр с тимлоком. Цифры оборота — черновые, финал в Monte-Carlo
отчёте (фаза 2). Лотерейные 5% создателю не меняются (там PvP).

**Банкролл ≠ кошелёк создателя.** Банкролл — баланс контракта, выплаты
игрокам гарантирует код; у контракта НЕТ функции вывода баланса на owner.
Создатель достаёт капитал только через LP-долю по общим правилам
(`withdraw` с guard покрытия активных спинов) и `claimCreatorFees()`.
На bootstrap весь банкролл = капитал создателя (казна → депозит, доля
100%), но после чужих депозитов это смешанный капитал: 300 создателя
превращаются в N% долей, edge поднимает цену доли всем пропорционально.
«Забрать всё» нельзя — можно вывести только свою долю, и это видно on-chain.
Внутри одного баланса — раздельные регистры: escrow игроков / LP principal
(включая долю создателя) / edge-буфер (растит цену доли) / accrued
creatorFeeShare (до claim). freeBankroll для maxBet = баланс минус
обязательства (escrow + покрытие активных спинов).

**Выход, баг, миграция — runbook декомиссии (создатель всегда может
вернуть свой капитал):**
1. *Обычный выход:* `withdraw(100% доли)` — одна tx. Задержка только при
   активных чужих спинах (guard): resolve ~2 с, worst case expireRefund
   через 256 блоков ≈ 3 мин → полный вывод 300 + edge. Локов/вестинга нет.
2. *Баг:* `pause()` мгновенно (без тимлока) — новые ставки стоп; активные
   разрешаются/refund-ятся; затем вывод своей доли → контракт брошен.
   Escrow игроков не может застрять (expireRefund) by design.
3. *Смена механики:* owner-параметры — тимлок 24ч, без деплоя. Immutable-часть
   (paytable/веса/сид) — только новый контракт: pause → ~3 мин → withdraw
   100% → deposit в SlotsV2. Доли не мигрируют автоматически, каждый LP
   решает сам.
4. *Невозвратное по дизайну:* выплаченные призы, claim'нутый feeShare,
   principal ДРУГИХ LP (он их). Риск «закирпиченного withdraw'а багом»
   сведён процессом (testnet → adversarial-тесты → мейннет) и малым
   bootstrap (300 = cap радиуса взрыва неизвестного бага — урок
   пост-мортема V1).
## 5. Фронтенд (эскиз)

**Лобби-размещение (решено):** слоты — featured-баннер НАД сеткой лотерейных
карт (не четвёртая карта в ряду: solo vs мультиплеер — разные механики).
Состав баннера: мини-барабаны с лёгкой цикличной анимацией (как «огонёк»
лобби), «Jackpot ×100 · RTP 95% · provably fair», банкролл/TVL, бегущий фид
последних спинов, кнопка PLAY NOW → /slots. Реализация — компонент
SlotsPreviewBoard по образцу GamePreviewBoard (та же тема, isLight, size).
LP-дашборд и депозит-кнопка живут на /slots, НЕ на главной (главная =
играть, депозиты — внутри игры). Баннер — фаза 5, вместе с самими слотами.

**Player journey (турбо, TVL ≥ 1000, bet 1) — ТЗ-сценарий:**
попап `spinSeries(10×1)` → escrow 10 → полоса 10 мини-раундов, результаты
появляются по мере майнинга блоков (~0.75 c каждый, прогрессивный счётчик
сессии) → на ~T+10 c кипер шлёт `resolveSeries` → баннер итога + кнопка
Verify (10 строк вывода blockhash→seed→символы→выплата). Один попап на
сессию; отмена невозможна (escrow до конца); при TVL < ~300 серия скрыта,
игрок живёт в solo (попап на каждый спин). Пример удачной сессии: 10 спинов,
одна тройка ⭐×20 + шесть пар → +22 USDT чистыми за ~10 c.

- Маршрут `/slots` (тип «Slot machine»), та же тема/кошелёк/USDT-approve,
  что у лотереи; карточка на лобби — как у лотерейных тиров + live-фид
  последних спинов.
- Машина: 3 барабана (DOM-анимация с замедлением, как «огонёк» в лобби),
  кнопка SPIN, выбор ставки (0.5/1/5), авто-спин (N раз, стоп на
  джекпоте/лимите), счётчик «следующий resolve через ~2 c».
- Панель Provably fair: для каждого спина показывает betBlock, хеш блока,
  сид-формулу и как символы вычислились — проверяемо на BscScan за минуту.
- LP-дашборд: мой банкролл-доля, цена доли, доход, deposit/withdraw.
- Состояния: spinning → resolving → result; обработка expireRefund и
  «есть незакрытый спин» (кнопка Resolve).
